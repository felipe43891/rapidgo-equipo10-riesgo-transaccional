# ADR-002 - Ejecución local de PySpark en Windows con winutils y aislamiento de checkpoints por capa

- **Fecha:** 2026-10-30
- **Estado:** Aceptado
- **Equipo:** Equipo 10 - Riesgo Transaccional

## Contexto / problema
Al integrar el job de procesamiento en tiempo real (`spark/streaming_job.py`) con PySpark 3.5.1 consumiendo del topic `rapidgo.payments.events` (Kafka en Docker sobre Windows), la ejecución real falló en tres puntos consecutivos:
1. **Fallo de librerías nativas de Hadoop en Windows:** Spark no iniciaba y arrojaba el error `HADOOP_HOME and hadoop.home.dir are unset` al intentar crear los directorios de checkpoint y escribir archivos Parquet locales.
2. **Colisión de `checkpointLocation` entre streams:** Tanto la capa `raw` como `processed` escribían la entidad `eventos` usando la ruta `datalake/checkpoints/{nombre}`. Al arrancar la consulta de `processed`, Spark detenía la consulta de `raw` (`WARN StreamingQueryManager: Stopping existing streaming query [...] as a new run is being started`), provocando que `spark.streams.awaitAnyTermination()` cerrara el proceso inmediatamente con `0` filas escritas.
3. **Bloqueo en `JavaSparkContext` con interfaces virtuales de Docker Desktop:** El método `.getOrCreate()` se quedaba bloqueado intentando enlazar el driver a la interfaz de red virtual de Windows/Docker si no se forzaba la dirección loopback.

## Opciones consideradas
1. **Opción A — Ejecución nativa en Windows con `winutils` (`hadoop-3.3.x`), fijación de driver local y checkpoints por `{capa}_{nombre}`:** Configurar `HADOOP_HOME=C:\hadoop` con `winutils.exe` y `hadoop.dll`, enlazar el driver de Spark a `127.0.0.1` y separar las carpetas de checkpoint por capa y tabla (`datalake/checkpoints/{capa}_{nombre}`).
2. **Opción B — Contenedorizar Spark en `docker-compose.yml`:** Añadir un servicio `spark-streaming` con la imagen `apache/spark:3.5.1-python3` y configurar un doble listener en Kafka (`localhost:9092` externo y `kafka:29092` interno).
3. **Opción C — Migrar todo el entorno de desarrollo a WSL2 (Ubuntu):** Instalar Java 17 y Python 3.12 dentro de WSL2 manteniendo Kafka en Docker.

## Decisión tomada
Se eligió la **Opción A** para el desarrollo y validación funcional de la Semana 2:
- Instalación de binarios `winutils.exe` y `hadoop.dll` (Hadoop 3.3.x compatible con PySpark 3.5.1) en `C:\hadoop\bin` declarando `HADOOP_HOME` en las variables de entorno.
- Modificación de `escribir()` en `spark/streaming_job.py` para nombrar cada stream (`queryName(f"{capa}_{nombre}")`) y aislar su checkpoint en `f"{lake}/checkpoints/{capa}_{nombre}"`.
- Configuración explícita de `.master("local[*]")`, `spark.driver.host=127.0.0.1`, `spark.driver.bindAddress=127.0.0.1` y monitoreo activo de excepciones por micro-batch.

## Evidencia utilizada
- **Log del fallo antes del cambio:**
  `26/10/30 16:18:30 WARN StreamingQueryManager: Stopping existing streaming query [id=03b5643f-054b-4c85-94cd-cdb01616c2ba, runId=cc184d6a-2a6a-419e-8311-1f3d9107bfea], as a new run is being started.` seguido de `raw: 0` y `processed: 0`.
- **Verificación posterior al cambio (commit `53a289f` en rama `feat/spark-streaming`):**
  - El job de Spark levantó los 4 streams simultáneamente (`raw_eventos`, `processed_eventos`, `curated_kpis_por_pedido`, `curated_alertas_por_usuario`).
  - Conteo real leído con Pandas sobre los archivos Parquet generados: `raw: 123` eventos y `processed: 123` eventos.
  - Ejecución de suite de pruebas con `pytest -v`: `30 passed in 0.46s` (incluyendo las 9 pruebas de `spark/test_reglas.py`).

## Consecuencias / trade-offs
- **Positivas:** Desbloqueo inmediato de la ejecución local en Windows sin descargar imágenes adicionales de varios cientos de MB ni modificar los listeners actuales de Kafka en `docker-compose.yml`; aislamiento garantizado del estado de cada stream en el Data Lake.
- **Negativas / Trade-offs:** Cada integrante que ejecute Spark de forma nativa en Windows debe configurar `C:\hadoop\bin` y `HADOOP_HOME` en su máquina. Para la orquestación con Airflow en la Semana 3 se evaluará empaquetar los servicios en Docker si se requiere ejecución desatendida en contenedor.
